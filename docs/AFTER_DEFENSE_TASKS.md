# Задачи после защиты

Эти задачи не обязательны для текущей демонстрации. На защите используется
стабильный `demo`-режим, а авторизация и аккаунты продолжают работать через backend.

## 1. Подготовить live-сценарий чата

### Решение перед началом

- Если на защите достаточно показать интерфейс переписки, оставить `demo`: он уже
  сохраняет сообщения отдельно для каждого аккаунта и бронирования.
- Если нужен именно серверный live-чат, заранее подготовить двух пользователей,
  объявление и бронирование. Без бронирования диалог намеренно недоступен.

### Что сделать для полноценного live-показа

1. Создать отдельные тестовые аккаунты гостя и владельца.
2. Создать объявление и серверное бронирование между этими аккаунтами.
3. Проверить чтение и отправку сообщений через `ChatController` и `ChatService`.
4. Проверить, что после перезагрузки сообщения остаются в PostgreSQL.
5. Проверить запрет доступа третьего пользователя к чужому диалогу.
6. Добавить понятное пустое состояние и инструкцию, если бронирований ещё нет.

### Критерий готовности

Гость и владелец видят один диалог, обмениваются сообщениями, после перезагрузки
история сохраняется, а посторонний пользователь получает отказ в доступе.

## 2. Сделать серверную службу поддержки

### Минимальный полезный вариант

1. Добавить сущность `SupportTicket` со ссылкой на пользователя, категорией,
   описанием, приоритетом, статусом и датами создания/обновления.
2. Добавить таблицу PostgreSQL через миграцию Entity Framework Core.
3. Добавить API создания обращения для авторизованного пользователя.
4. Добавить API списка и смены статуса обращения для администратора.
5. Подключить существующую форму поддержки к live API.
6. В админке показать поиск, фильтр по статусу и карточку обращения.

Отправка писем, операторский чат и хранение вложений не входят в минимальный
вариант. Имя вложения можно убрать либо хранить как метаданные до появления
файлового хранилища.

### Критерий готовности

Пользователь создаёт обращение, оно сохраняется в PostgreSQL и появляется в
админке. Администратор может изменить его статус, а обычный пользователь не может
просматривать чужие обращения.
