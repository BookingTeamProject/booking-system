# Администрирование

Панель находится по адресу `/admin`; вход выполняется через обычную `/login`.
Авторизация и администрирование всегда работают с сервером, включая demo-сборку.

## Первый главный администратор

Перед первым запуском API задайте переменные окружения процесса или контейнера:

```text
BootstrapAdmin__Email=<отдельный email администратора>
BootstrapAdmin__Password=<собственный пароль длиной не менее 12 символов>
```

Максимум пароля — 72 байта UTF-8 (ограничение BCrypt). Не коммитьте пароль.
API создаст единственного системного администратора после миграций. Пароль хранится
как BCrypt-хеш. Если email уже занят, запуск завершится ошибкой: существующая учётная
запись не получает административные права автоматически. При последующих запусках
пароль не сбрасывается, второй главный администратор не создаётся. После создания
можно убрать bootstrap-переменные из окружения. Обычный вход останется доступен.

Это встроенный механизм создания аккаунта, а не общий известный пароль в коде.
В GitHub Actions секреты нужно явно передать окружению запускаемого API-контейнера;
одно создание GitHub Secret не передаёт его приложению. Конфигурация деплоя из main
в этой работе не изменялась. В рабочей базе главный аккаунт автоматически не создавался
во время локальной проверки: тестирование выполнялось в отдельной базе.

## Возможности и правила

| Операция | Главный Admin | Назначенный Admin |
| --- | --- | --- |
| Поиск по имени/email/ID, фильтры, страницы | Да | Да |
| Статистика пользователей, жилья, броней и отзывов | Да | Да |
| Роли User/Landlord/Moderator у обычных аккаунтов | Да | Да |
| Назначить Admin, изменить другого Admin | Да | Нет |
| Блокировка, удаление, восстановление обычного аккаунта | Да | Да |
| Изменить свой аккаунт через административные операции | Нет | Нет |
| Удалить, заблокировать или понизить главного Admin | Нет | Нет |
| Читать чужую переписку благодаря роли Admin | Нет | Нет |

Moderator — зарезервированная роль; отдельная модераторская панель пока не реализована.
Удаление логическое: история бронирований, отзывов и сообщений сохраняется, аккаунт
можно восстановить. Это не механизм окончательного удаления персональных данных.
Восстановление не снимает установленную ранее блокировку; её снимают отдельно.

Изменение роли, блокировка, удаление и восстановление увеличивают `AuthVersion` и
аннулируют refresh-токен. На каждом авторизованном запросе сервер сверяет пользователя
с БД. Старый access-токен больше не принимается; после смены роли нужен новый вход.
Жильё заблокированного/удалённого владельца скрывается из каталога, новые брони
запрещены. Существующая история не уничтожается. Административные действия пишутся
в серверный журнал с ID исполнителя и целевого аккаунта; отдельного журнала в UI нет.

## HTTP API

- `GET /api/admin/users?search=...&role=0&status=active&page=1&pageSize=20`
- `GET /api/admin/statistics`
- `PUT /api/admin/users/{id}/role` — JSON-число 0/1/2/3.
- `PUT /api/admin/users/{id}/blocked` — JSON boolean.
- `DELETE /api/admin/users/{id}` — логическое удаление.
- `POST /api/admin/users/{id}/restore` — восстановление.

Статусы поиска: active, blocked, deleted, all. Максимальный размер страницы — 100.
Ответы списка не содержат хешей паролей и токенов. Проверки доступа выполняются
сервером независимо от видимости кнопок на frontend.
