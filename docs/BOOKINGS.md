# Бронирование: первый рабочий сценарий

## Правила

- Бронируется всё помешкання, без продажи отдельных комнат.
- Даты передаются как `YYYY-MM-DD`, без преобразования в UTC timestamp.
  Для определения сегодняшнего дня сервер использует UTC.
- Интервал полуоткрытый: `[checkIn, checkOut)`. Новый заезд в день выезда разрешён.
- Срок — 1–365 ночей, заезд не в прошлом. Количество гостей — 1–`Route.MaxGuests`.
  Для существующих объявлений миграция задаёт вместимость 4: владельцам нужно
  проверить и исправить её перед использованием на реальных объектах.
- Цена берётся из БД: ночи × цена за ночь + 300 UAH уборка + 150 UAH сервисный сбор.
  Сборы пока фиксированные. Цена и сборы сохраняются в брони; изменение объявления
  не пересчитывает уже оформленную бронь. `totalPrice` из браузера не используется.
- `Pending` и `Confirmed` занимают даты. PostgreSQL exclusion constraint
  `EX_Bookings_NoOverlap` предотвращает пересечения, включая параллельные запросы.
  Миграция устанавливает стандартное расширение `btree_gist`; пользователь миграций
  должен иметь право на его установку, либо DBA должен установить его заранее.
- Бронь создаётся как `Pending`. Только владелец может подтвердить/отклонить заявку.
  Гость может отменить свою ожидающую или подтверждённую бронь; владелец —
  подтверждённую. После дня заезда изменения закрыты. Отменённую/отклонённую бронь
  нельзя восстановить сменой статуса. Конкурентные смены статуса используют
  compare-and-swap по прежнему статусу.
- После выезда подтверждённая бронь возвращается как `Completed`.
  Ожидающие заявки не истекают автоматически: до реализации срока ожидания их
  должен отклонять владелец или отменять гость.
- Удаление объявления с бронями запрещено, чтобы сохранялась история.
- Оплата и возвраты денег в этом сценарии не выполняются.

## API

| Метод | Адрес | Назначение |
|---|---|---|
| POST | `/api/bookings/quote` | Проверка дат и серверный расчёт |
| POST | `/api/bookings` | Создание заявки, HTTP 201 |
| GET | `/api/bookings/my` | Брони текущего гостя |
| GET | `/api/bookings/host` | Брони объектов текущего владельца |
| GET | `/api/bookings/route/{id}/unavailable-dates` | Занятые периоды без персональных данных |
| PUT | `/api/bookings/{id}/status` | `{ "status": "Confirmed", "reason": null }` |
| GET | `/api/routes/mine` | Объявления текущего владельца |

Расчёт и создание принимают `{ routeId, checkIn, checkOut, guests }`.
Проверка доступности не резервирует даты — при создании возможен HTTP 409.
Нужен JWT, кроме публичного чтения занятых периодов. Чужая смена статуса — 403,
неверные даты — 400, отсутствующее объявление — 404, пересечение дат или уже
изменённый статус — 409.

## Ручная проверка

1. Зарегистрируйте владельца и гостя в разных профилях браузера.
2. Владелец создаёт объявление с ценой 1000 UAH и вместимостью 2.
3. Гость выбирает 3 ночи и 2 гостей: сервер должен показать 3450 UAH.
4. После отправки гость и владелец видят одну заявку `Pending`.
5. Другой гость не может занять пересекающиеся даты, но может заехать в день выезда.
6. Владелец подтверждает, гость обновляет список и видит `Confirmed`.
7. Гость отменяет: даты освобождаются, запись остаётся в истории вместе с причиной.
8. Перезапустите API и обновите страницы: статус и цена сохраняются.
9. Регистрация с ролью `Admin`/`Moderator` отклоняется сервером.

## Границы этого этапа

В кабинеты подключены реальные списки объявлений и бронирований. Старые фиктивные
календарные блокировки, вымышленные заявки и кнопки, сообщавшие о сохранении только
в React, не используются в этих рабочих экранах. Полноценный календарь тарифов,
блокировка дней хозяином — возможные расширения. Приватная переписка участников
бронирования реализована. Реальная финансовая аналитика и платёжная интеграция
исключены из объёма диплома: финансовый модуль остаётся демонстрационным.
